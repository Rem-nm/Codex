# 流量统计与限速

## 方向定义

客户端视角为准：

```text
上传 = 客户端 → Shadowsocks 服务器
下载 = Internet → Shadowsocks 服务器 → 客户端
```

在服务器外部网络接口上，上传包的目的端口是节点端口；下载包的源端口是节点端口。因此 tc 规则分别匹配 ingress `dst_port` 和 egress `src_port`。

## 持久化

`ss-manager-traffic.timer` 每分钟运行一次：读取每个节点、每个方向的共享 tc action bytes 计数，与上次持久化基线做差，把当前周期、累计字段和新基线一起原子写入 `traffic.json`。任何一个 action 查询失败都会放弃整次采样，不会把查询错误当成 0。设备重启会使 tc 规则消失，采样器会先重建并验证规则，再重置内核基线；外部删除规则也会触发同样的恢复流程。

## 周期结算

每个节点有自己的重置日（1-28），以 `last_reset_at` 和 `next_reset_at` 判断。timer 的 `Persistent=true` 让系统重启后补运行；维护逻辑在一次运行中处理所有已错过的周期。达到配额时只变更状态，不删除节点、不删除凭据、不删除数据。

## 限速

tc 使用 flower filters；IPv4 与 IPv6 使用相邻但不同的优先级，避免内核按协议区分过滤器时发生冲突。每个节点的上传、下载各有一个共享 action，所有地址族、传输协议和默认路由接口都按 index 绑定到同一 action，所以 `police rate` 是节点方向的聚合硬限速；0 使用只放行并计数的 `gact pass`。action 带确定性 index 和 128-bit cookie，规则计划保存 action 身份与接口列表。清理时逐条验证 cookie、绑定数及精确 flower handle；同优先级的外部过滤器不会被删除，发现混合所有权或额外绑定会拒绝操作。配置事务失败时按旧节点数据库重建旧规则。

注意：统计和限速依赖检测到的默认路由接口；多出口或策略路由服务器应先在系统设置里确认接口范围。
